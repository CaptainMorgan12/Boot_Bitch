# Boot Bitch legacy (Debian Etch / KDE 3.5 era)

Experimental legacy frontend for the pre-systemd, pre-Qt4 era. It targets
**Debian 4.0 "Etch" on KDE 3.5** (bash 3.1, no `/etc/os-release`, no
`pkexec`, no `lsblk`/`findmnt`) and ships as a **separate artifact**,
`boot-repair-legacy` `0.2.25-etch1`, built natively in the Etch guest. The
modern Qt6 `boot-repair` tree is untouched and is not buildable or installable
on Etch.

This is the helper-only + launcher milestone: the ported helper keeps the same
command surface and the same `Repair tool <key>: available|unavailable|<reason>`
/ `Repair change status <key>: ...` evidence contract as the modern helper,
so a later Qt3 frontend can consume it unchanged.

## Launcher

```
boot-repair-legacy [options] [helper-command [args...]]
```

With no arguments the launcher opens a `dialog` menu (falling back to a plain
console menu when `dialog` is absent or the terminal is not interactive) and
runs the helper with elevation. With a helper command it elevates and runs
that command directly.

Documented commands:

```
validate <disk> <root>                confirm the selected root is supported
diagnose <disk> <root> all            read-only diagnostics (capability probes)
fs-inspect <disk> <root>              read-only filesystem inspection
repair <disk> <root> fix-broken       safe repair: restore broken package state
repair <disk> <root> dpkg-configure   safe repair: finish pending dpkg configuration
repair <disk> <root> initramfs        safe repair: rebuild the target initramfs
repair <disk> <root> apt-update       safe repair: refresh package metadata (mirror-gated)
```

Useful options: `--tui` (force the menu), `--helper PATH`,
`--print-helper`, `--list-commands`, `--dry-run` (print the command that would
run), `--no-elevate` (caller is already root). `--help` shows all of them.

Elevation order: `gksu --sudo-mode`, `gksudo`, `sudo`, `su` (plain TTY
prompt). No passphrase is ever placed on a command line. A desktop-session
launch with no terminal opens the menu inside `x-terminal-emulator`, `konsole`
or `xterm`. The helper is discovered from `--helper`, then
`BOOT_REPAIR_LEGACY_HELPER`, then `/usr/sbin/boot-repair-legacy-helper`, then
source-tree-relative paths. The launcher never weakens the helper's own
runtime preflights.

## Compatibility target and gated features

Availability is always decided by live probe evidence in the helper, never by
a distribution check. On an Etch-era host the expected picture is:

| Feature | Etch behaviour |
| --- | --- |
| `validate`, `diagnose`, `fs-inspect` | available (read-only) |
| `dpkg-configure`, `fix-broken` | available with simulation-first guards |
| `apt-update`, `upgrade` | probe-gated; unavailable without a reachable, trusted APT source |
| `initramfs` | available after validation (`update-initramfs` 0.85i) |
| `grub` | available through the guarded GRUB-legacy branch (`update-grub` only; `menu.lst` backup, entry-preservation guard and rollback) |
| `display` | read-only evidence only (sysvinit/KDM); repair not implemented |
| `efi`, `dkms`, `extlinux`, `bootstack` | unavailable with the exact missing prerequisite as the reason |
| `host-*`, `shell`, file copy, snapshots | unavailable on Etch (missing `unshare`/`timeout`/`rsync`/Btrfs evidence) |
| LUKS `unlock` | available (cryptsetup 1.0.4, LUKS1); stdin only, never argv |

## Packaging

Build the `.deb` **inside the Etch guest** (native `dpkg-deb` 1.13.26 +
`fakeroot` 1.5.10, no CMake/CPack):

```sh
scripts/package-legacy.sh                  # -> Development/build-legacy-package/boot-repair-legacy_0.2.25-etch1_amd64.deb
scripts/package-legacy.sh --output DIR
scripts/package-legacy.sh --dry-run        # stage + validate only; works on any host
```

The script refuses a real build off-Etch with a clear message and never
installs anything; `--dry-run` stages the tree and prints the generated
control metadata. It runs `legacy/port.sh --check` (drift gate) when that tool
is present, and `bash -n` on the staged helper and launcher.

**Helper source coordination.** The port agent owns the generated helper. The
packager's default discovery order is
`legacy/boot-repair-helper.sh`, then
`legacy/helper/boot-repair-helper-legacy.sh`, then
`legacy/boot-repair-helper-legacy.sh`, then
`scripts/legacy/boot-repair-helper-legacy.sh`, then
`scripts/boot-repair-legacy-helper.sh`; if the port lands somewhere else, point
the packager at it with the documented variable:

```sh
LEGACY_HELPER_SRC=legacy/somewhere/boot-repair-helper.sh scripts/package-legacy.sh
```

`LEGACY_HELPER_INSTALL` (default `/usr/sbin/boot-repair-legacy-helper`) is
substituted into the installed launcher, so a different install path stays
consistent. `LEGACY_ARCH`, `LEGACY_OUTPUT_DIR` and `LEGACY_STAGE_DIR` override
the architecture and directories.

Package metadata: `Depends: libqt3-mt | libqt3c102-mt, bash (>= 3.1),
util-linux, mount, e2fsprogs, grub, gksu | sudo, cryptsetup`; `Recommends:`
`dialog`, `dosfstools`, `lvm2`, `mdadm`, `initramfs-tools`, `rsync`;
`Suggests:` `kdelibs4c2a`, `konsole | xterm`. The Qt3 runtime alternative is
kept so a future Qt3 frontend needs no dependency transition.

## Testing

`scripts/test-legacy-package-contract.sh` (registered as the fast
`boot-repair-legacy-package-contract` ctest) checks the staging layout, the
control fields and dependency list, launcher syntax and command list, and the
dry-run path, using a fixture helper so it runs anywhere. It never builds or
installs a package.

`legacy/tests/test-port-contract.sh` (fast `boot-repair-legacy-port-contract`)
runs `legacy/port.sh --check`, asserts the generated helper is bash-3.1 syntax
clean, exercises every compat shim and the evidence-based feature gating, and
proves the modern helper is untouched. `legacy/tests/test-smoke.sh` (fast
`boot-repair-legacy-smoke`) runs read-only `validate`/`diagnose` against a
synthetic `/etc/os-release`-less Etch root and covers the dpkg status fallback,
the GRUB-legacy rollback and the 13-key capability report. Neither test touches
a real disk, builds a package or needs root.
